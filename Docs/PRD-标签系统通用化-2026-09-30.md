## 一、现状盘点与问题分析

### 1.1 现有 12 类标签（全部偏专业向）

安全/开发密集：sensitive（敏感）、vuln（漏洞编号）、otp（验证码）、hash（哈希指纹）、ip（IP 地址）、cmd（命令行）、stack（堆栈日志）、config（配置）
弱通用：link（链接）、email（邮箱）、snippet（代码）、path（文件路径）

### 1.2 问题：普通用户的剪贴板内容没有对应标签

典型非技术用户的剪贴板流：快递单号、银行账号、会议时间、地址、聊天的书摘、发票抬头、日程、待人办事清单……在现有 12 类下几乎全部**无标签可打**，筛选条对他们形同虚设。

### 1.3 设计原则（对齐既有架构）

1. **精度红线**：宁可漏打不打错。新标签全部走「强特征正则/结构化验证」路线，不做模糊猜测（误报会毁掉筛选信任）
2. **性能纪律**：识别器保持与既有 detect 家族一致——单正则优先，成本 O(n) 单遍；总量控制
3. **架构兼容**：沿用 TAG_PRIORITY 价值序 + TAG_ORDER + computeTags 的 try/catch 隔离 + enabled 开关体系；i18n 走 tagXxx 驼峰 key 约定；筛选条自动获得新标签（零 UI 改动）
4. **默认全开**：新标签默认启用，用户可在设置里关掉（与 12 类既有行为一致）

## 二、新增标签提案（10 类，按价值分层）

### 2.1 通用生活/办公层（普通用户价值最高，6 类）

| id | 名称（zh/en） | 识别特征（强特征，误报率设计目标 <1%） | 典型来源 |
|----|----|----|----|
| `tracking` | 快递单号 / Tracking No. | 结构化单号族：SF+15位数字、YT+13位、JD+13位纯数字、EMS 13位字母数字、9 开头邮政 13 位等（带前缀白名单+长度+校验位组合） | 电商/物流短信、聊天里的运单号 |
| `bankcard` | 银行卡 / Bank Card | 13-19 位纯数字 + **Luhn 校验通过** + 分段模式（4-4-4-4 等常见空格/横线分隔变体先去分隔符再验）。复用既有 luhnCheck 基建 | 网银、客服、聊天里发卡号 |
| `phone` | 手机号 / Phone | 中国大陆手机号：`1[3-9]\d{9}`，前后是非数字边界；容忍 `+86`/`86` 前缀与分隔符变体 | 通讯录、登记表单、聊天 |
| `idcard` | 身份证 / ID Card | 18 位（含 X 校验位）+ **GB 11643 校验位算法验证**；15 位旧号不启用（误报高） | 实名登记、人事表格 |
| `meeting` | 会议/日程 / Meeting | 强模式组合：日期时间词（周X/明天/X月X日）+ 时间点（HH:MM）+ 会议动词（开会/会议/评审/例会/ deadline/meeting/call）同段共现 | 聊天、邮件、日历通知 |
| `address` | 地址 / Address | 强模式：省/市/自治区开头 + 路/街/巷/号/栋/层/室 结尾组合，长度 ≥10 且含 ≥2 个地址关键词 | 快递、外送、登记信息 |

### 2.2 泛办公增强层（与现有类互补，4 类）

| id | 名称（zh/en） | 识别特征 | 说明 |
|----|----|----|----|
| `url-cred` | 账号凭据 / Credentials | 「账号/密码/用户名/password/passwd + 邻近冒号值对」组合模式（对齐 otp 的邻近窗口思路） | 归入 sensitive 前置信号而非独立敏感类：先标凭据，敏感词命中仍叠加 sensitive |
| `todo` | 待办 / Todo | 行首勾选/待办符号（`- [ ]`、`TODO:`、`待办：`、`记得`）或清单结构（≥2 个连续序号行） | 与 snippet 不互斥 |
| `color` | 颜色值 / Color | `#RGB/#RRGGBB/#AARRGGBB`、`rgb()/rgba()/hsl()` 完整语法 + 数值范围校验 | 设计协作场景高频 |
| `uuid` | UUID / UUID | 8-4-4-4-12 十六进制标准格式（大小写不敏感），纯 UUID 而非泛 guid | 订单号/工单/许可证高频 |

### 2.3 不做的类型（记录否决理由）

- **发票/税号**：规则与地址重叠度高，且格式版本多，误报风险 > 价值
- **聊天语义分类**（"这个人说了啥"）：需要 NLP 模型，违背"纯正则、零依赖"纪律
- **日历 ICS/vCard 解析**：出现频率太低，不值得独立标签

## 三、TAG_PRIORITY 合并方案

新 10 类插入后的完整优先序（**加粗**为新增）：

```text
sensitive, vuln, otp, url-cred,
bankcard, idcard, tracking, phone,
cmd, stack, config, meeting, todo,
ip, hash, uuid, color, address,
link, email, snippet, path
```

排序依据（延续 v2 价值序逻辑）：
- 凭据/资金/证件类（泄密代价高）紧跟安全三兄弟之后
- 结构化单号类（精确可检索）居中
- 泛模式类（meeting/todo/color/address）偏后
- link/email/snippet/path 保持既有相对位置在尾部

存储上限 MAX_TAGS=8 与展示截断逻辑不变：普通条目通常命中 0-2 个新标签，不会挤爆。

## 四、UI/交互影响评估

- **筛选条**：标签总数 12→22，筛选条横向滚动区已支持（scrollbar-width none），无 UI 改动；但 22 个 chip 的排列顺序 = TAG_PRIORITY，建议筛选条内按「新增通用类靠前展示」做视觉分组（可选优化，不阻塞本版）
- **设置面板**：自动打标签设置若为逐类开关 UI，需为新 10 类补开关（前端工作量主要在这里）
- **i18n**：新增 20 个 key（10 类 × 中英），走既有 tagXxx 驼峰约定
- **持久化**：旧数据无新标签字段，无需迁移——新标签只影响增量内容的自动打标；用户可对旧条目手动补标（既有能力）

## 五、风险与缓解

| 风险 | 缓解 |
|------|------|
| 快递单号/手机号正则误报（普通长数字串） | 前缀白名单 + 边界断言 + 校验位；宁可漏检 |
| 身份证校验位误报 | 仅 18 位启用校验位算法；15 位直接不识别 |
| 22 类全开后的性能 | 新增识别器全部单遍正则，基准测试纳入验收（64KB 混合文本 < 8ms，较现有 5ms 预算放宽） |
| 用户不想看到生活类标签 | 沿用既有 per-tag 开关，默认全开但可关 |

## 六、验收标准（测试工程师直接引用）

1. 每类新标签 ≥8 条正负用例（正例必中、负例必不中、边界值）
2. 真实语料回归：现有 432+ 条既有用例全绿（新标签不得改变旧内容既有打标结果）
3. 性能：64KB 混合文本 computeTags < 8ms（含新 10 类）
4. 筛选条/设置开关/i18n 三处 UI 联动无回归
