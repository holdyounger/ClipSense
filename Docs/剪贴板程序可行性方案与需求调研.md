# 基于 KeySense 框架实现「剪贴板程序」可行性方案与需求调研

> 版本：调研稿 V0.1
> 日期：2026-08-27
> 作者：产品调研（待产品负责人确认）
> 结论速览：**技术可行，建议独立新项目（复用框架），不建议在 KeySense 内硬塞功能**

---

## 一、调研背景与目标

当前 KeySense 是一款基于 **Electron 28** 的跨平台「快捷键提示器」，核心能力：

- 无边框 / 透明 / 始终置顶窗口
- 全局快捷键 `Ctrl+Shift+K` 唤出/隐藏
- 系统托盘常驻后台
- 活动窗口进程检测（active-win）、边缘吸附、状态机轮询
- 数据分层：内置 JSON + 用户自定义 JSON（userData 目录，已实现 CRUD）

本次调研要回答：**能否基于这套框架低成本扩展出一个「剪贴板历史 / 剪贴板管理」程序？** 以及它是否值得做、怎么做。

---

## 二、可行性结论（TL;DR）

| 维度 | 结论 | 说明 |
|------|------|------|
| 技术可行性 | ✅ 高 | Electron 内置 `clipboard` 模块，剪贴板读写/监听原生可用，无需新增原生依赖 |
| 框架复用度 | ✅ 高（约 60%） | 窗口体系、托盘、全局快捷键、配置存储、自定义数据机制可直接复用 |
| 核心难点 | ⚠️ 中 | 剪贴板「变化监听」跨平台无官方事件，需轮询兜底；图片/富文本序列化需额外设计 |
| 产品价值 | ⚠️ 待验证 | 需求真实存在但竞品密集，需差异化定位 |
| 建议 | ✅ 独立新项目 | 避免污染 KeySense 定位，复用框架即可 |

## 三、现有框架能力盘点（可复用资产）

> 以下均基于 `src/` 实际代码核实，非臆测。

### 3.1 直接复用（几乎零成本）

| 能力 | 位置 | 复用方式 |
|------|------|---------|
| 无边框透明置顶窗口 | `index.js` `createWindow()` | 剪贴板面板天然需要置顶弹出 |
| 全局快捷键注册 | `index.js` `registerGlobalShortcut()` | 改成 `Ctrl+Shift+V` 之类唤出 |
| 系统托盘 + 菜单 | `index.js` `initTray()` / `_buildTrayMenu()` | 常驻后台、右键退出 |
| 边缘吸附/自动隐藏 | `edge-detector.js` | 剪贴板面板同样需要失焦隐藏 |
| 状态机轮询框架 | `index.js` `_setOverlayState()` | 剪贴板「监听」可复用轮询节奏 |
| 用户配置持久化 | `config-store.js`（electron-store） | 存剪贴板容量、历史条数等 |
| 用户自定义数据 CRUD | `data-manager.js`（本次已实现） | 可改造成「剪贴板历史存储」 |

### 3.2 关键差异点（需要新增）

| 需求 | KeySense 现状 | 剪贴板程序需要 |
|------|--------------|--------------|
| 数据来源 | 静态 JSON 快捷键库 | 系统剪贴板实时内容 |
| 监听机制 | 无需监听（主动轮询前台窗口） | **需要监听剪贴板内容变化** |
| 数据规模 | 几百条静态数据 | 可能几千~几万条历史记录 |
| 内容类型 | 纯文本（key/action/category） | 文本/图片/富文本/文件 |
| 持久化 | JSON 文件够用 | 需要更大容量 + 可能上 SQLite |

## 四、技术可行性分析

### 4.1 Electron 剪贴板能力（原生可用）

Electron 内置 `clipboard` 模块，以下能力**无需新增第三方原生依赖**：

- `clipboard.readText()` / `writeText()` — 纯文本
- `clipboard.readImage()` / `writeImage()` — 图片（转 `nativeImage`）
- `clipboard.readHTML()` / `writeHTML()` — 富文本
- `clipboard.clear()` — 清空

⚠️ **关键缺口**：`clipboard` **没有跨平台的「变化事件」**。
- Windows 可用 `clipboard.on('changed')`？—— ❌ **Electron clipboard 模块不支持 `on('changed')`**，这是常见误区。
  - （⚠️ 待核实：不同 Electron 版本是否有 `clipboard` 事件，需查 Electron 28 官方文档确认。当前结论：**无可靠跨平台 change 事件**。）
- 主流做法是**轮询对比**：定时读取当前剪贴板内容，与上次记录做哈希比对，变化则归档一条历史。

### 4.2 剪贴板变化监听的实现方案

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **A. 轮询比对**（推荐） | 每 300~800ms 读剪贴板，比对 hash | 跨平台、稳定、实现简单 | 有延迟、应用全屏/锁屏时可能漏读 |
| B. 原生事件钩子 | Windows 用 Win32 剪贴板监听（`AddClipboardFormatListener`） | 实时、精确 | 需原生模块（回到 robotjs 式编译坑，**不推荐**） |
| C. 混合 | 轮询为主 + 前台激活时强制读一次 | 兼顾体验与稳定 | 逻辑略复杂 |

**建议采用方案 A 或 C**，并复用 KeySense 已经验证过的「状态机 + setInterval 轮询」模式——这与现有 `edge-detector` 的轮询架构高度一致，开发者可平滑迁移。

### 4.3 持久化方案

- **短期（MVP）**：沿用 `data-manager` 思路，把历史存到 `userData/clipboard-history.json`，环形缓冲保留最近 N 条（如 500 条）。
- **中期**：条数过大、需检索时，引入 `better-sqlite3`（⚠️ 注意：这也是**原生模块**，会重新引入 node-gyp 编译问题，需在 CI 配置 VS 工具链或使用其预编译二进制）。
  - ⚠️ 待核实：`better-sqlite3` 是否有 Electron 28 的预编译二进制。

### 4.4 图片 / 富文本的额外复杂度

- 图片：`clipboard.readImage()` 得到 `nativeImage`，可 `toPNG()` / `toDataURL()` 存储，但**体积大**，持久化需做大小上限（如单图 ≤ 5MB）。
- 富文本：需处理 HTML 渲染安全（XSS），面板里展示富文本要过 `CSP`（当前 KeySense 的 CSP 是 `style-src 'self' 'unsafe-inline'`，渲染外部富文本需谨慎）。
- 文件复制：`clipboard` 对「文件列表」支持有限，跨平台差异大，建议 MVP 先**只做文本 + 图片**，文件留待二期。

## 五、产品需求调研

> ⚠️ 以下为需求侧初步判断，**未做真实用户访谈/问卷**，标「待核实」部分需产品后续验证。

### 5.1 目标用户与场景

| 场景 | 痛点 | 我们的价值 |
|------|------|-----------|
| 频繁复制粘贴的开发/办公用户 | 系统剪贴板只存一条，覆盖即丢失 | 历史回溯，随时找回 |
| 多段内容拼接整理 | 需要来回切换复制 | 快速选择历史条目粘贴 |
| 截图后临时存图 | 截图很快被覆盖 | 图片历史暂存 |

### 5.2 核心功能需求（MVP vs 增强）

**MVP（必做）**
- [ ] 监听剪贴板变化，自动记录历史（文本优先）
- [ ] 全局快捷键唤出面板（复用 `Ctrl+Shift+` 系列）
- [ ] 历史列表展示（时间 + 内容预览）
- [ ] 点击条目 → 写回剪贴板并粘贴
- [ ] 单条删除 / 清空
- [ ] 容量上限与环形覆盖

**增强（二期）**
- [ ] 搜索历史内容
- [ ] 收藏/置顶常用片段
- [ ] 图片剪贴板支持
- [ ] 多设备同步（需后端，成本高，谨慎评估）
- [ ] 富文本格式保留

### 5.3 差异化定位（竞品相关）

> ⚠️ **待核实**：以下竞品信息基于模型印象，**未在本会话查证**官方资料，切勿直接引用到对外材料。需产品人工核实。

- 市场上存在 Windows 自带的剪贴板历史（Win+V）、以及 Ditto、CopyQ 等第三方工具。（⚠️ 以上均为印象，需逐一核实当前状态、功能、是否仍维护）
- **差异化方向建议**：
  1. 与 KeySense 同一生态，快捷键提示 + 剪贴板联动（如「按应用显示常用剪贴模板」）
  2. 轻量、无广告、本地优先、隐私友好（数据不出本机）
  3. 自定义模板片段（把「快捷键」概念扩展为「可粘贴的片段」）

## 六、架构方案建议

### 6.1 推荐：独立新项目（复用框架模式）

```
clipboard-manager/          # 新仓库
├── src/
│   ├── main/
│   │   ├── index.js        # 主进程（复用 KeySense 窗口/托盘/快捷键骨架）
│   │   ├── clipboard-monitor.js  # 剪贴板轮询监听（新增核心模块）
│   │   ├── history-store.js      # 历史持久化（对标 data-manager）
│   │   └── config-store.js       # 复用
│   └── renderer/
│       ├── index.html / main.js / main.css
│       └── preload.js
└── package.json            # 去掉 robotjs 等不需要的依赖
```

### 6.2 为什么独立而非合并进 KeySense

1. **定位清晰**：KeySense = 快捷键提示；剪贴板 = 历史管理，两者目标不同。
2. **依赖差异**：剪贴板历史量大，未来可能引 SQLite（原生模块），与 KeySense「零原生依赖」的轻量目标冲突。
3. **维护成本**：合并会让 KeySense 的状态机、窗口逻辑被迫承载剪贴板逻辑，增加回归风险。
4. **但共享组件**：窗口骨架、托盘、配置存储等可抽取为公共模块（或直接 copy 改造，当前规模抽取成本高于收益）。

## 七、风险与待办

### 7.1 技术风险

| 风险 | 等级 | 应对 |
|------|------|------|
| 剪贴板监听无跨平台事件，轮询有延迟 | 中 | 方案 C（轮询 + 前台强制读） |
| 原生模块（SQLite 等）重新引入 node-gyp 编译坑 | 中 | MVP 用 JSON 存储，避开原生模块 |
| 图片/富文本体积与安全 | 中 | 一期只做文本，图片限尺寸 |
| 隐私合规（剪贴板可能含密码/敏感信息） | 高 | 本地存储、不上传、可一键清空、明确隐私说明 |

### 7.2 待核实清单（产品需落实）

- [ ] Electron 28 的 `clipboard` 是否真有 change 事件（查官方文档）
- [ ] 竞品现状：Ditto / CopyQ / Windows 内置剪贴板历史的功能对比
- [ ] 目标用户真实需求（问卷/访谈，而非印象）
- [ ] `better-sqlite3` 是否有 Electron 28 预编译二进制
- [ ] 文件复制的跨平台支持边界

## 八、下一步建议

1. **先出一个 1 页 Demo 验证核心风险**：用最小实现验证「轮询监听剪贴板 + 面板展示 + 点击回写」这条链路，确认 Electron 剪贴板能力满足预期（建议 2~3 天 spike）。
2. **产品侧补需求调研**：针对 5.2 的待核实项做真实用户访谈，确定 MVP 范围。
3. **架构决策**：确认走「独立新项目」路线后，立项。
